# Замер скорости скачивания

[English](README.md) | **Русский**

Небольшая консольная утилита для замера скорости скачивания. Она скачивает
один и тот же URL несколько раз (по умолчанию 10), строго по одному запросу за
раз, замеряет время каждой загрузки и число реально полученных байтов и выводит
итоговую скорость.

Решения по неоднозначным местам задания собраны в разделе
[Как трактуется задание](#как-трактуется-задание).

## Быстрый старт

```bash
git clone https://github.com/mikholand/internet-speed-test.git
cd internet-speed-test
python -m venv .venv
source .venv/bin/activate        # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
python main.py "https://speed.cloudflare.com/__down?bytes=5000000"
```

Результат — в последней строке отчёта, например
`Download speed:   9.22 MB/s (73.77 Mbps)`. Если в macOS или Linux команда
`python` не найдена, используйте `python3`. Подробности для каждой системы — в
разделах [Установка](#установка) и [Запуск](#запуск).

## Возможности

- По умолчанию ровно **10 последовательных запросов**: каждый начинается только
  после того, как тело предыдущего ответа скачано полностью.
- Точный замер времени через `time.perf_counter()` — от отправки запроса до
  получения последнего байта тела.
- Объём считается по **фактически полученным байтам**, а не по заголовку
  `Content-Length`.
- Время, объём и скорость каждого запроса, затем итог: общий объём, общее время,
  среднее время запроса и итоговая скорость в МБ/с (рядом — в Мбит/с).
- Один HTTP-клиент на весь замер: соединение держится открытым и
  переиспользуется.
- Понятные сообщения и ненулевые коды выхода при некорректном URL, ошибках
  соединения, таймаутах, HTTP 4xx/5xx и пустых ответах.
- Одна зависимость (`httpx`), один файл с кодом и тесты, которым не нужен
  интернет.

```bash
python main.py <URL> [--count N] [--timeout SECONDS]
```

### Примеры

```bash
# По умолчанию: 10 последовательных запросов, таймаут 30 секунд
python main.py https://example.com/image.jpg

# Эндпоинт Cloudflare для тестов скорости отдаёт ровно запрошенное число байтов
python main.py "https://speed.cloudflare.com/__down?bytes=5000000"

# Большая картинка (с редиректом на CDN; редиректы проходятся автоматически)
python main.py https://picsum.photos/seed/speedtest/3840/2160

# Меньше запросов и короче таймаут
python main.py https://example.com/image.jpg --count 5 --timeout 10

# Справка
python main.py --help
```

Если в URL есть `?` или `&`, возьмите его в кавычки, иначе оболочка может
истолковать эти символы по-своему.

Используйте ресурс размером хотя бы в несколько мегабайт. На маленьких файлах
время определяется задержкой сети (обменом пакетами туда и обратно), а не
пропускной способностью, поэтому скорость получится заметно ниже реальной.

## Как трактуется задание

Формулировка задания короткая, поэтому некоторые пункты можно понять
по-разному. Ниже — принятые решения и причина каждого.

| Пункт | Решение | Почему |
|---|---|---|
| Единица скорости («мб/с» в задании) | Мегабайты в секунду, десятичные (1 МБ = 10⁶ байт), выводятся первыми; рядом то же значение в Мбит/с | «мб/с» чаще всего означает мегабайты в секунду; Мбит/с добавлены, потому что в них продают тарифы |
| «Дожидаться ответа» | Запрос заканчивается, когда получен последний байт тела, а не заголовки | Скорость должна отражать саму передачу данных |
| «10 последовательных запросов» | По умолчанию ровно 10, каждый начинается только после полного чтения предыдущего тела; без дополнительного «прогревочного» запроса. Параметр `--count` есть, но по умолчанию — 10 | Прогрев означал бы 11 запросов к серверу |
| Объём скачанного | Фактически полученные байты тела; HTTP-заголовки не считаются, `Content-Length` не используется | Заголовка может не быть, или он может не совпадать с телом; тело — это и есть запрошенные данные |
| Формула скорости | Суммарный объём / суммарное время запросов; паузы между запросами не учитываются | Среднее скоростей отдельных запросов завышает результат (см. [Единицы и формулы](#единицы-и-формулы)) |
| Установка соединения (в задании нет) | Учитывается: в первый запрос входят DNS, TCP и TLS, остальные переиспользуют соединение | Это часть настоящего запроса, а переиспользование соединения — обычное поведение HTTP-клиента |
| Редиректы (в задании нет) | Проходятся; их время входит во время запроса | Ссылки на картинки часто ведут на CDN через редирект |
| Таймаут (в задании нет) | 30 секунд без сетевой активности, а не ограничение на всё время загрузки | Медленный, но рабочий канал — это результат, а не ошибка |
| Неудачный запрос (в задании нет) | Замер останавливается, итог не печатается, код выхода 1 | Скорость по меньшему числу загрузок или с подставленными нулями вводила бы в заблуждение |
| Пустой ответ (в задании нет) | Считается ошибкой | Измерять нечего |
| Язык (в задании нет) | Python 3.10+ | Задание не называет язык |

## Как устроен замер

1. На весь замер создаётся один `httpx.Client`. Его пул держит соединение
   открытым, поэтому следующие запросы не тратят время на его установку.
2. Для каждого запроса `i` (1…N), строго по очереди:
   - таймер запускается (`time.perf_counter()`) прямо перед отправкой
     запроса `GET`;
   - проверяется статус ответа (4xx/5xx — ошибка);
   - тело читается потоком, длины всех полученных кусков складываются
     (`response.iter_raw()`), поэтому размер — это то, что реально пришло,
     независимо от заголовка `Content-Length`;
   - таймер останавливается сразу после получения последнего байта тела.
3. Результат печатается уже после остановки таймера, поэтому время между
   запросами в замер не попадает: учитывается только время самих HTTP-запросов.

Замеренное время `tᵢ` включает отправку запроса, обработку на сервере, переходы
по редиректам (если они есть) и скачивание всего тела. Замеренный объём `bᵢ` —
только тело: HTTP-заголовки и накладные расходы TLS не учитываются, так что
результат — полезная скорость на уровне приложения.

Запросы отправляются с заголовком `Accept-Encoding: identity`, то есть сервер
просят не сжимать тело. Тогда замеренный объём равен реальному размеру ресурса.
Если сервер всё же сожмёт ответ, будут посчитаны сырые (сжатые) байты,
прошедшие по сети: именно они и были скачаны.

## Единицы и формулы

Все единицы **десятичные (СИ)** — так же считают провайдеры и сервисы замера
скорости:

| Единица | Значение |
|---|---|
| 1 КБ / 1 МБ / 1 ГБ | 10³ / 10⁶ / 10⁹ байт |
| 1 Кбит/с / 1 Мбит/с / 1 Гбит/с | 10³ / 10⁶ / 10⁹ бит в секунду |
| 1 МБ/с | 8 Мбит/с |

В выводе программы они записаны латиницей: `KB`, `MB`, `MB/s`, `Mbps`.

Основная единица — **мегабайты в секунду (МБ/с)**: задание просит скорость в
«мб/с», а МБ/с легко соотнести с размером файлов. В скобках то же значение в
**мегабитах в секунду (Мбит/с)**, потому что в них продают тарифы. Обе величины
остаются в «мега»-единицах даже на медленном канале (`0.50 MB/s`). Меньший
префикс получает только значение, которое иначе округлилось бы до `0.00`:
например, `2.12 KB/s` вместо вводящего в заблуждение `0.00 MB/s`.

> Файловые менеджеры, например Проводник Windows, показывают размеры в двоичных
> единицах (1 МиБ = 1 048 576 байт), но подписывают их «МБ». Один и тот же файл
> в 5 000 000 байт здесь — 5.00 MB, а в Проводнике — «4,76 МБ».

Для `N` запросов, где запрос `i` занял `tᵢ` секунд и принёс `bᵢ` байт:

```text
Всего скачано     B = b₁ + b₂ + … + bₙ                      (байт)
Общее время       T = t₁ + t₂ + … + tₙ                      (секунд)
Среднее время       = T / N                                 (секунд)
Скорость            = B / T / 1 000 000                     (МБ/с)
                    = B × 8 / T / 1 000 000                 (Мбит/с)
```

Скорость в строке каждого запроса — `bᵢ / tᵢ`, в МБ/с.

Итоговая скорость — это **суммарный объём, делённый на суммарное время**, а не
среднее скоростей отдельных запросов. Например, 1 МБ за 1 с плюс 1 МБ за 3 с —
это 2 МБ / 4 с = **0,50 МБ/с**. Среднее двух скоростей (1,00 и 0,33 МБ/с) дало бы
0,67 МБ/с. Результат был бы завышен, потому что быстрый запрос получил бы такой
же вес, как медленный.

## Обработка ошибок

Замер работает по принципу **«всё или ничего»**: первый неудачный запрос
останавливает тест. Неудачный запрос никогда не засчитывается как нулевое время
или нулевой объём, частичный итог не печатается. Ошибки выводятся в stderr, а
программа завершается с ненулевым кодом. Сообщения программа печатает на
английском.

| Ситуация | Пример сообщения | Код выхода |
|---|---|---|
| Некорректный URL (нет схемы, не http/https, нет хоста, неверный порт) | `error: argument url: invalid URL 'example.com/image.jpg': expected an absolute URL starting with http:// or https://` | 2 |
| Некорректный `--count` / `--timeout` | `error: argument -c/--count: expected a positive integer, got '0'` | 2 |
| Неизвестный хост / соединение отклонено | `Error: Request 1/10 failed: could not connect to the server ([Errno 11001] getaddrinfo failed)` | 1 |
| Таймаут подключения | `Error: Request 1/10 failed: timed out while connecting to the server` | 1 |
| Сервер перестал присылать данные (таймаут чтения) | `Error: Request 1/10 failed: timed out while waiting for data from the server` | 1 |
| HTTP 4xx / 5xx | `Error: Request 3/10 failed: server responded with HTTP 503 Service Unavailable` | 1 |
| Пустое тело (например, HTTP 204) | `Error: Request 1/10 failed: the server returned an empty response body` | 1 |
| Обрыв соединения посреди загрузки, слишком много редиректов, другие ошибки протокола | `Error: Request 1/10 failed: network error (peer closed connection without sending complete message body (received 400000 bytes, expected 1000000))` | 1 |
| Прерывание по Ctrl+C | `Interrupted by user.` | 130 |
| Вывод закрыт раньше времени, например передан в `head` | Тихое завершение без трассировки | 1 |

Некорректные аргументы отклоняются ещё до первого сетевого запроса. Код 2 —
стандартный код `argparse` для ошибок в аргументах.

Всё, чего нет в этой таблице, было бы ошибкой в самой утилите. Такие исключения
намеренно не перехватываются, чтобы их трассировка оставалась видна (Python
завершается с кодом 1).

### Таймаут

`--timeout` ограничивает, сколько утилита ждёт **установки соединения** и
**каждой следующей порции данных**. Общую длительность загрузки он не
ограничивает. Большой файл на медленном, но рабочем канале будет замерен до
конца, а сервер, который перестал отвечать, обнаружится за `--timeout` секунд.
Жёсткий лимит на всё время превратил бы в ошибку медленный канал — то есть
именно то, что должен показывать тест скорости.

Редиректы проходятся автоматически (до 20 на запрос). Время на редиректы входит
во время запроса.

## Разработка и тесты

Установите инструменты разработки (pytest, pytest-cov, ruff, mypy) в
виртуальное окружение:

```bash
pip install -r requirements-dev.txt
```

Проверки, на которых держится качество проекта:

```bash
python -m pytest --cov    # тесты с покрытием строк и ветвлений; падают, если покрытие ниже 100%
ruff check .              # линтер
ruff format --check .     # форматирование
mypy                      # строгая проверка типов
```

Настройки инструментов лежат в `pyproject.toml`. Кроме них в этом файле ничего
нет: проект — это один скрипт, а не устанавливаемый пакет.

Тестам не нужен интернет. Большинство из них подменяют HTTP через
`httpx.MockTransport`. Сквозные тесты поднимают временный HTTP-сервер на
`127.0.0.1`, а некоторые запускают `main.py` отдельным процессом. Покрыто:

- подсчёт байтов (потоковое тело без `Content-Length`, неверный
  `Content-Length`);
- строгая последовательность: каждый ответ дочитывается до конца, прежде чем
  начнётся следующий запрос;
- остановка на первой ошибке с номером запроса в сообщении;
- HTTP-ошибки (включая статус без текстового пояснения), пустое тело, ошибки
  соединения и таймауты;
- формула скорости (суммарный объём / суммарное время) и форматирование единиц;
- проверка аргументов, Ctrl+C, закрытый вывод и коды выхода настоящего
  процесса;
- на реальных сокетах: переиспользование соединения (все 10 запросов по одному
  keep-alive соединению), таймаут до заголовков и посреди тела, переход по
  редиректу и тело, оборванное посреди загрузки. В последнем случае замер должен
  остановиться с кодом 1 и не повторять запрос.

## Проектные решения

**Почему `httpx`.** `requests` тоже справился бы, но `httpx` подходит для этой
задачи лучше:

- `httpx.Client` в роли контекстного менеджера управляет пулом соединений и
  временем его жизни;
- потоковый API (`client.stream()` и `iter_raw()`) отдаёт тело ровно в том
  виде, в каком оно пришло, поэтому подсчёт байтов получается простым;
- в нём раздельные таймауты на подключение и чтение и подробная иерархия
  исключений (`ConnectError`, `ConnectTimeout`, `ReadTimeout`,
  `HTTPStatusError`, …), которые легко превратить в понятные сообщения;
- `httpx.MockTransport` позволяет тестировать без сети и без дополнительных
  библиотек для подмен;
- библиотека полностью типизирована.

**Почему один файл.** Утилита — около 330 строк с одной задачей. Код уже разбит
на небольшие функции, у каждой одна ответственность (разбор аргументов → замер
запроса → серия запросов → итоги → форматирование), так что отдельные модули
добавили бы только импорты. Если утилита вырастет, эти функции можно без
изменений перенести в модули.

**Без параллельности.** Нет ни `asyncio`, ни потоков, ни процессов. Запросы идут
в обычном цикле, и каждая загрузка дочитывается до конца, прежде чем цикл
продолжится.

## Ограничения

- Утилита измеряет скорость одного HTTP-соединения. Сервисы замера скорости,
  которые открывают несколько параллельных соединений, на быстрых каналах могут
  показывать большие значения.
- Результат зависит не только от вашего канала, но и от сервера: от его
  удалённости, загрузки и пропускной способности. Для самых показательных цифр
  выбирайте быстрый и близкий хост, например CDN.
